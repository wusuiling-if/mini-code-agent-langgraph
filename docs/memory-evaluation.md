# 通用记忆架构与四路对照评测

本文说明如何验证记忆系统是否真的带来提升，而不是只展示“能召回”的成功样例。

## 被测架构

生产代码位于 `src/mini_code_agent/memory_retrieval.py`，结构如下：

```text
认证记忆存储
  → 作用域、状态、有效时间、权限、来源硬过滤
  → BM25 / 精确 cue / cue 重叠 / 认证关系图并行候选
  → RRF 融合和质量分
  → 候选分差、歧义与相关性门控
  → use_memory 或 no_memory
  → 带来源、权限和作用域的有限上下文包
```

领域策略只调整阈值和风险偏好。`coding`、`research`、`personal_assistant`、
`customer_service` 与 `generic` 共用同一份数据结构和检索代码。

这里没有使用 embedding。这样做不是否定向量检索，而是先验证作用域、时间、图关系和
克制机制本身的增益。后续可以把 embedding 作为新的候选路由加入 RRF，对照开关单独测量，
不能替代硬过滤和 `no_memory` 门控。

## 四种方案的可操作定义

所有方案读取同一份记忆语料并回答同一批问题。

| 方案 | 定义 |
| --- | --- |
| 无记忆 | 永远不注入长期记忆。它不会误注入，但无法回答必须依赖历史的问题。 |
| 纯召回 | 对摘要和 cue 做词/中文双字 TF cosine，固定返回 Top-3；没有作用域、生命周期、证据权限或克制门。 |
| 传统三层 | 工作记忆（最近记录）+ 情景记忆 + 语义/程序长期记忆；保留合理的显式作用域和 active 状态过滤，以词法相似度合并；没有有效时间窗、来源权限、图扩展和歧义门。 |
| 新架构 | 证据约束的时态混合检索：硬过滤、多路候选、RRF、图扩展、逐条阈值和明确克制。 |

“传统三层”是本仓库为可复现消融给出的具体实现，不代表所有被称为三层记忆的系统。
“纯召回”也是确定性的 Top-k 代理，不等同于某个特定 embedding 模型。

## 数据集与防止自我欺骗

固定套件包含 16 个问题，覆盖编码、研究、个人助理、客服及通用场景。样例包括：

- 同一关键词在不同租户、用户、项目和仓库中的作用域冲突；
- 已被替代的旧事实、已经过期的状态和未来才生效的合同；
- 外部网页内容试图获得更高动作权限；
- 必须沿认证关系边才能取得的研究结论；
- 两个未决候选造成的歧义；
- 天气、体育和税率等记忆库无法回答的问题。

每个问题预先登记目标卡片、禁止注入的卡片、是否应该克制以及端到端答案关键词。
评测不调用模型生成标签，也不使用被测系统给自己打分。

## 指标

- `decision_accuracy`：应该回答时取得目标卡片，应该克制时返回 `no_memory`。
- `answerable_recall_at_3`：可回答问题的目标记忆是否进入前三条。
- `expected_abstention_recall`：应该克制的问题中实际克制的比例。
- `harmful_injection_rate`：注入过期、跨作用域、权限不足或明确冲突记忆的问题比例。
- `context_precision`：注入上下文中目标记忆所占比例。
- `average_memories_injected`：每个问题平均注入多少条记忆。

验收门要求：新架构的决策准确率至少比最强基线高 15 个百分点，错误注入率不超过 5%，
应克制问题的召回率至少 80%。任一条件不满足，命令以非零状态退出。

## 可选真实模型评测

真实模型评测会对四种方案分别调用模型，完整 16 题共 64 次请求。API Key 只从环境变量读取，
不要把密钥写入命令参数、报告或聊天消息。

OpenAI 示例：

```bash
export OPENAI_API_KEY='...'
.venv/bin/python -m evals.run_memory_model_comparison \
  --provider openai \
  --model YOUR_MODEL \
  --output /tmp/memory-model-report.json
```

DeepSeek 示例：

```bash
export DEEPSEEK_API_KEY='...'
.venv/bin/python -m evals.run_memory_model_comparison \
  --provider deepseek \
  --model deepseek-flash
```

可先用 `--max-cases 2` 做 8 次请求的冒烟测试。模型被要求只使用给定记忆，证据不足时严格输出
`NO_MEMORY`。可回答问题按预注册关键词评分，克制问题按严格的 `NO_MEMORY` 字符串评分，
避免再调用一个模型充当主观裁判。

模型评测受模型版本、服务端行为和随机性影响，因此报告结果，不作为默认 CI 硬门；确定性离线
评测才是回归门。

## 长期记忆纵向评测

静态16题只能测某个时间点的选择质量。纵向套件会模拟120轮持续写入：第0轮埋入目标记忆，
之后加入120条高置信、高重要度、具有相同关键词但属于其他用户、租户、仓库或研究项目的
干扰记忆。期间还会发生两次事实替代、一次明确遗忘、一个有效期到期，以及一条需要沿图关系
获得的早期结论。

```bash
.venv/bin/python -m evals.run_memory_longitudinal
.venv/bin/python -m evals.run_memory_longitudinal --json
```

固定协议最终包含132张卡片和29个探针。稳定事实分别在距离1、10、50和120轮时查询，形成
`0–2`、`3–20`、`21–60`、`61+`四个年龄桶。指标同时记录总体正确率、长期保留率、错误
注入率以及检索端到端P50/P95延迟。

当前离线结果：

| 方案 | 总体准确率 | 长期保留率 | 错误注入率 |
| --- | ---: | ---: | ---: |
| 无记忆 | 17.2% | 0.0% | 0.0% |
| 纯召回 | 62.1% | 100.0% | 27.6% |
| 传统三层 | 86.2% | 100.0% | 3.5% |
| 新架构 | **100.0%** | **100.0%** | **0.0%** |

新架构在四个年龄桶中的保留率均为100%，相对最强基线总体提升`13.8`个百分点。加入作用域
优先候选缩减和批量状态解析后，132张卡片规模下本机新架构P50/P95选择延迟约为
`1.64/2.95`毫秒；延迟只作观察值，不设跨机器硬门。

这项评测证明的是“记忆已经正确写入后，经历大量后续写入仍能存储、更新、遗忘和检索”。它
不是实际等待数月，也不测模型是否能从自由对话中自动抽取出正确记忆。Runtime 当前只有
显式 opt-in、receipt 驱动的确定性验证流程记忆；这套纵向评测没有经过该准入路径，也不测
自由文本抽取、归并和巩固，因此报告中的`automatic_memory_formation`仍明确为`false`。

## 长期对话读取诊断

参考 [LongMemEval](https://arxiv.org/abs/2410.10813) 的信息提取、跨 session 推理、时间推理、
知识更新和拒答能力，仓库另提供一个不使用 embedding 的 120-session 小型诊断：

```bash
.venv/bin/python -m evals.run_memory_long_conversation
```

它把 timestamped session 作为已经认证的 `user` 事件显式写入，再测试称呼/数据库更新、过敏
事实、两段 session 合并、两次预约的时间比较、明确遗忘、跨用户隔离、助手侧信息和未知问题
拒答。首次运行为 `8/9`，暴露出“我的”被当作强 exact cue 后错误回答未知护照问题；排除泛化
所有格 cue 并加入未参与定位的驾照签发机关 holdout 后，离线检索为 `10/10`，store 完整性通过。

真实 DeepSeek 读取对照共 30 次调用：

| 读取方式 | 正确率 | 平均上下文字符 |
| --- | ---: | ---: |
| 最近 8 个 session | 30% | 2,648 |
| 完整 120-session 历史 | 90% | 35,808 |
| 证据时态记忆 | 90% | 342 |

记忆路径用约少 `99.0%` 的上下文达到与完整历史相同的单次正确率；但检索 `10/10` 不等于
reader `10/10`：模型仍把一条明确的榛子过敏证据回答为 `NO_MEMORY`。这项结果只证明“显式
认证 session 写入后的读取和管理能力”，不是官方 LongMemEval 分数，更不证明生产 `mca chat`
已经具备自由对话抽取。当前真正缺口是 session decomposition、事实化写入和可审计更新，而不是
继续扩大检索 Top-k。

## 结果感知控制评测

静态检索只能回答“哪些记忆相关”，不能回答“此时使用它是否有净收益”。v0 控制评测在相同
候选上加入运行阶段、认证结果反馈、token 成本和反记忆角色：

```bash
.venv/bin/python -m evals.run_memory_control
.venv/bin/python -m evals.run_memory_control --json
```

六个确定性用例全部通过。对照中，静态检索返回的已知有害候选数为 `1`，控制层读取三次带
可信证据的失败/有害结果后降为 `0`；其余用例覆盖反例显式警告、无关查询克制、连续失败后
重查，以及影子策略既不注入也不训练活跃策略。实现细节见
[结果感知的记忆控制层](memory-control.md)。

这不是 contextual bandit、强化学习或开放世界泛化实验：策略权重为手工设定，数据为仓库内
固定样例，没有模型调用，也没有生产流量。它的价值是先把决策、反馈证据和安全边界变成可测
接口，为后续影子日志和离线策略评估建立基线。

### 复杂三文件真实模型复测

为降低简单任务的天花板效应，第二套 fixture 要求同时修复客户折扣、折后免运费阈值、加急

记忆提供仓库历史结算规则，不提供测试输出。三种条件各运行 3 次，并轮换执行顺序：

| 条件 | 验证成功 | 平均步骤 | 步数序列 | 平均读文件 | 平均编辑 | 编辑后失败 |
| --- | ---: | ---: | --- | ---: | ---: | ---: |
| 无记忆 | 3/3 | 7.00 | 7, 7, 7 | 7.00 | 3.00 | 0 |
| 静态检索 | 3/3 | 7.00 | 6, 6, 9 | 5.00 | 3.00 | 0 |
| 控制记忆 | 3/3 | **6.33** | 6, 6, 7 | 5.00 | 3.00 | 0 |

控制记忆相对无记忆和静态检索平均少 `9.5%` 模型步骤；静态和控制均少 `28.6%` 读文件调用。

### 去除手写记忆后的自然经验迁移

上一节仍然手写了正确/冲突规则并预灌结果反馈，不能公平代表完整记忆架构。自然迁移协议改为：

1. DeepSeek 在无记忆条件下完成训练任务并通过真实测试；
2. 系统从验证后的三个实现文件 diff 自动形成唯一经验卡，cue 只由训练任务文本自动提取；
3. 在文件名、函数名、费率、阈值和金额均变化的未见 fixture 上运行三路对照；
4. 新控制层的反馈只来自各次真实验证结果，不手工标记有益或有害。

训练任务 9 步完成并通过验证。迁移结果如下：

| 条件 | 验证成功 | 平均步骤 | 步数序列 | 平均读文件 | 平均工具调用 | 编辑后失败 |
| --- | ---: | ---: | --- | ---: | ---: | ---: |
| 无记忆 | 3/3 | 7.67 | 9, 7, 7 | 7.00 | 14.00 | 0 |
| 原证据时态检索器 | 3/3 | **6.00** | 6, 6, 6 | **4.00** | **11.00** | 0 |
| 新结果感知控制层 | 3/3 | 7.00 | 7, 7, 7 | 7.00 | 14.00 | 0 |

这次原架构明确优于新控制层：相对无记忆，原检索器平均少 `21.7%` 模型步骤、`42.9%` 读文件
和 `21.4%` 工具调用；新控制层只少 `8.7%` 模型步骤，读文件和工具调用没有改善。相对原架构，
新控制层多 `16.7%` 模型步骤、`75%` 读文件和 `27.3%` 工具调用。

两条记忆路径选择的是同一张自动形成的卡片。原检索上下文为 1595 字符，控制层包装为 1660
字符；控制层随后记录了 3 次真实成功反馈，但三次行为都保持 7 步。因此退化不来自错误召回，
更可能来自控制包装中的角色、期望效用和谨慎说明改变了模型使用经验的方式。该因果解释仍需

该结果支持保留原架构为默认路径，把新控制器降级为可关闭的实验层；至少在新的盲测证明收益
之前，不应迁移默认行为。

上下文为 1,798 字符，远低于 16K 上限，说明新 renderer 没有破坏这项迁移收益。

宿主无关 portability 套件另有 5/5 通过，覆盖普通 CI 证据形成、非 MCA 端到端宿主、硬上下文
