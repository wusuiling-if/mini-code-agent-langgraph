# v0.3.2 Promotion Design

Date: 2026-07-21

## Goal

Give the released `0.3.2` package a small, high-signal launch that attracts
technical evaluation and real feedback without manufacturing engagement or
overstating the offline benchmark.

## Current state

- Pull request `#2` is merged into `main` at `b807f56`.
- Annotated tag `v0.3.2`, the matching GitHub Release, and PyPI `0.3.2` are
  public.
- The exact PyPI package passes a clean install plus `mca --version`,
  `mca demo`, `mca doctor --sandbox none`, and `pip check`.
- The repository first screen already contains a real no-key demo, focused
  differentiators, English and Chinese documentation, security guidance, and
  issue forms.
- The public repository has no homepage URL or Discussions feedback surface.

## Authorization and boundaries

The maintainer approved the GitHub-first launch approach on 2026-07-21 and
explicitly authorized promotion after release.

Codex may:

- improve the existing GitHub Release notes using verified repository facts;
- set the repository homepage to the PyPI project page;
- enable GitHub Discussions, create one launch-and-feedback discussion, and pin
  it when GitHub exposes that operation;
- publish once to a relevant third-party community when the account is already
  authenticated and the current community rules permit the post;
- record GitHub traffic and engagement baselines for later comparison.

Codex must not:

- ask for Stars, votes, comments, karma, or reciprocal engagement;
- fabricate users, adoption, performance, security guarantees, or model-quality
  results;
- describe the deterministic offline suite as SWE-bench or autonomous coding
  quality evidence;
- mass-post identical copy, cross-post across multiple subreddits, use private
  messages, or bypass authentication and moderation controls;
- publish generated or AI-edited text to Hacker News or V2EX, whose current
  rules prohibit it;
- include credentials, private repository content, local home paths, raw
  trajectories, or Undo journals in public material.

## Positioning

The launch centers on one testable promise: this is a compact, inspectable
coding-agent runtime that binds submission to a passing user-selected test on
the current workspace fingerprint.

Supporting differentiators are:

1. redacted, resumable trajectories with stale verification invalidated after
   resume;
2. HMAC-authenticated, conflict-aware Undo;
3. a deterministic no-key `mca demo` path;
4. explicit security boundaries, fail-closed verification, and a reproducible
   offline policy-conformance suite.

The eleven-case `v0.3.2` benchmark may be reported only with its full boundary:
`11/11` deterministic offline runtime-policy cases passed, comprising nine
verified submissions and two expected refusals, with zero unexpected
submissions and zero unrelated changes. It does not measure model quality,
autonomous repair ability, provider behavior, real-world task success, or
SWE-bench performance.

## Channel design

### GitHub and PyPI: canonical facts

The GitHub Release becomes the canonical short launch page. It contains:

- the installation command and no-key demo command;
- the three principal security and lifecycle changes in `0.3.2`;
- the bounded benchmark result and disclaimer;
- links to PyPI, the changelog, security policy, and the feedback discussion.

The repository homepage points to the PyPI project page. Existing Issues remain
the actionable defect and feature-request system.

### GitHub Discussions: conversational feedback

Enable repository Discussions and create one pinned announcement titled
`mini-code-agent-langgraph 0.3.2: launch notes and technical feedback`.
The post links to the Release and PyPI, gives a two-command trial path, states
the benchmark boundary, and asks for technical feedback on verification,
trajectory recovery, Undo, sandbox ergonomics, and framework coupling. It does
not ask for Stars.

Do not create multiple empty categories or seed fake questions. Use GitHub's
default announcement category and keep Issues as the place for reproducible
bugs and scoped feature requests.

### Hacker News and V2EX: human-only handoff

Do not submit generated or AI-edited text. Provide the maintainer with verified
facts and the canonical links, but the maintainer must personally write and
submit any Show HN or V2EX `分享创造` post in their own words.

For Hacker News, the human submission must present the runnable project rather
than a routine patch announcement, begin with `Show HN`, and be posted only when
the maintainer is available to discuss it. For V2EX, the human post must disclose
maintainer affiliation, use the correct node, and contain original Chinese text.

### Reddit: one compliant attempt

Use at most one relevant community or designated self-promotion thread. Read
the current community rules immediately before posting, disclose that the
poster maintains the free MIT-licensed project, use a technical text post rather
than a bare link, and invite concrete feedback. If the browser is not already
authenticated or the community rules are ambiguous, stop without posting.

## Measurement

Capture a near-launch baseline and compare it after roughly seven quiet days:

- reach: repository views, unique visitors, and referrers;
- conversion: Stars and forks interpreted alongside meaningful views;
- activation: clones, Issues, Discussions, and concrete technical feedback.

No Star quota is a release criterion. Do not add runtime features merely to
move a launch metric during the observation window.

## Failure handling

- If a GitHub write is rejected, read the response, leave existing public state
  intact, and diagnose the exact permission or schema boundary before retrying.
- If Discussions cannot be pinned through the available API, keep the single
  announcement unpinned and report that limitation.
- If a third-party account requires sign-in, stop at that channel and ask the
  maintainer to authenticate in the selected browser; never request credentials.
- If a platform disallows generated text, do not publish or lightly paraphrase
  generated copy to evade the rule.
- Public posts and immutable release artifacts are never deleted and reposted
  merely to improve exposure.

## Verification

- Read back the repository homepage, Discussions state, Release body, and
  discussion URL through GitHub APIs.
- Confirm every public link resolves and every version reference is `0.3.2`.
- Scan public copy for Star/vote solicitation, unsupported benchmark claims,
  secret-like values, and local paths before publication.
- Record the exact URL and current state for each successful third-party post.
- Capture the first traffic/engagement snapshot after the GitHub launch changes.

## Out of scope

- paid promotion, ads, influencer outreach, newsletters, or direct messages;
- automated engagement, Star exchanges, vote solicitation, or multiple account
  activity;
- runtime features, benchmark expansion, website work, branding, or a new UI;
- publishing AI-generated or AI-edited text where community rules prohibit it.
