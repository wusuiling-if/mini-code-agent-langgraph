# v0.3.2 Trust and Benchmark Design

## Goal

Strengthen the project's central claim: a submitted patch is bound to an
explicit, non-empty authoritative test run against the current workspace. Make
that contract visible through a deterministic offline benchmark and protect the
repository and release path from avoidable supply-chain mistakes.

## Decision and Alternatives

The selected approach is a strict, fail-closed patch release:

- `mca run` requires both an explicit real model and `--test-command`;
- the calculator-specific mock remains an internal test/evaluation component
  and the implementation behind `mca demo`, not a general `run` model;
- `mca chat` remains useful without a test command in `/ask`, but `/code` and
  every non-read-only tool are unavailable until the session is restarted with
  an authoritative command;
- recognized zero-test output does not mint verification unless the user
  explicitly passes `--allow-zero-tests`;
- an eleven-case offline benchmark exercises policy and recovery behavior;
- repository workflows and GitHub settings add dependency monitoring, static
  analysis, immutable action pins, PR gates, and immutable release tags.

Two alternatives were rejected. Keeping an implicit DeepSeek or mock model
would preserve compatibility but hide provider choice or keep the misleading
calculator behavior. Automatically guessing a repository's test runner would
improve convenience but would make a security decision from incomplete
heuristics. An online multi-provider benchmark was also rejected because it
would mix model quality, network variance, cost, and runtime-policy behavior.

## CLI and Verification Contract

`mca run` is a coding operation, so its parser requires `--model` and
`--test-command`. Passing `--model mock` is rejected with guidance to use
`mca demo`. Resume requires the same explicit inputs; trajectories are audit
artifacts and do not become trusted configuration.

`mca chat` retains its current real-model default and accepts no test command
for read-only `/ask`. Attempting `/code` without one prints an actionable error,
keeps the controller in `/ask`, and does not dispatch the text as a coding turn.
The controller also blocks every non-read-only tool with
`TestCommandRequired`, so future REPL changes cannot bypass the command check.

`BashExecutor` accepts an optional authoritative command. `run_tests` fails
closed when it is absent. For recognized runner summaries, it records a
`tests_run` count on `ToolResult`; a successful process that reports zero tests
is converted to `NoTestsCollected`. The explicit `allow_zero_tests` option is
the only override. Unknown custom output continues to use the command's exit
code because pretending to infer a count from arbitrary shell output would be
misleading.

The initial recognized summaries are conservative:

- Python unittest: `Ran N test/tests`;
- pytest zero collection: `collected 0 items` or `no tests ran`.

## Offline Verified-Patch Benchmark

The benchmark uses scripted local model responses, disposable fixtures, the
production agent loop, the production executor, and no network or API key. It
measures runtime-policy conformance, not model intelligence.

The eleven cases are:

1. single-file repair;
2. exact two-file repair;
3. no-change explanation;
4. recovery from a failed edit;
5. premature submission blocked, then recovered;
6. stale verification invalidated by a later edit, then recovered;
7. failed authoritative test blocks submission;
8. zero discovered tests block submission;
9. disabled shell is refused while structured verification can recover;
10. safe checkpoint resume requires a fresh test;
11. authenticated undo restores the original file.

Expected refusals count as passing benchmark outcomes. Schema version 2 reports
`passed`, `outcome`, verification and refusal evidence, structured test runs,
expected/unrelated changes, lifecycle evidence, steps, tool calls, and duration.
Reports never contain raw trajectories, workspace contents, Undo records, keys,
or journal paths. Duration and platform metadata are informational; the
scenario plans and pass/fail results are deterministic.

CI writes the sanitized JSON report even when a case fails, uploads it for
seven days, and exposes no workspace or trajectory artifact. The README and
eval documentation state the benchmark's limits explicitly.

## Supply-Chain and Repository Policy

Repository changes include:

- weekly grouped Dependabot updates for Python and GitHub Actions;
- a reviewed, pinned `pip-audit` CI tool requirement;
- PR-only dependency review at high severity;
- Python CodeQL on `main`, pull requests, and a weekly schedule;
- full-SHA current GitHub Actions pins;
- CI concurrency cancellation, pip download caching, and job timeouts;
- workflow-policy tests that fail on mutable or unapproved actions, overly
  broad permissions, missing timeouts, or unsafe `pull_request_target` use.

After the branch workflows pass, GitHub settings enable vulnerability alerts
and security updates, require full action SHAs, protect `main` with PR plus
required checks and zero approvals for the solo-maintainer phase, and protect
`v*` tags from deletion or update. The owner retains an explicit emergency
bypass until a second trusted maintainer exists. The PyPI `v*` environment and
OIDC Trusted Publisher remain unchanged.

## Compatibility and Limits

This is intentionally breaking for implicit `mca run "task"` and CLI
`--model mock` users. The supported no-key path is `mca demo`. Chat without a
test command remains a read-only assistant. `--allow-zero-tests`, sandbox
disablement, shell enablement, dirty-worktree bypass, and confirmation bypass
remain explicit weakening flags and must be documented as such.

The release does not add TUI, MCP, multi-agent orchestration, provider plugins,
automatic test discovery, an online model leaderboard, or a LangGraph rewrite.

## Acceptance Criteria

- A recognized zero-test run cannot produce `verification_status=passed` by
  default, and a regression test demonstrates the original failure.
- `mca run` cannot start without an explicit model and test command and rejects
  mock with `mca demo` guidance.
- `mca chat` can answer in `/ask` without a test command but cannot enter or
  bypass `/code`.
- All eleven offline benchmark cases pass, report schema 2 JSON, and record zero
  unrelated changes and zero unexpected submissions.
- CI, package build, Twine validation, dependency audit, workflow policy tests,
  and the complete test suite pass.
- GitHub reports active `main` and `v*` protections plus enabled Dependabot
  alerts/security updates before this work is described as fully complete.
